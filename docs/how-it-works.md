# Как работает webhook-relay

## Зачем это вообще нужно

Вебхук — это когда одна система сама сообщает другой, что что-то произошло: «заказ создан», «оплата прошла». Технически это просто POST-запрос на чужой URL.

Проблема в том, что чужой сервер может лежать, тормозить или отвечать 500. Если отправлять вебхук прямо из кода приложения в момент события, то:

- пользователь ждёт, пока мы достучимся до чужого сервера;
- если тот упал — событие теряется;
- повторы приходится писать в каждом месте заново.

webhook-relay забирает эту работу на себя. Приложение один раз говорит «произошло событие такое-то» и сразу идёт дальше, а сервис сам доставит событие всем подписчикам и будет повторять, пока не получится.

## Из чего состоит

```
приложение ──POST /events──▶  API  ──▶  PostgreSQL  ◀── воркеры ──POST──▶ подписчики
```

Три таблицы:

- `subscriptions` — кто хочет получать события: URL, тип события (`order.created` или `*` для всех) и секрет для подписи;
- `events` — сами события: тип и JSON с данными;
- `deliveries` — одна строка на пару «событие + подписчик». Здесь и живёт вся логика: статус, сколько было попыток, когда следующая, последняя ошибка.

Код разложен по файлам:

| Файл | Что делает |
|---|---|
| `main.go` | Подключается к базе, запускает HTTP-сервер и воркеры, ловит Ctrl+C / SIGTERM |
| `api.go` | Обработчики HTTP-запросов |
| `worker.go` | Берёт доставки из базы, отправляет, решает что делать дальше |
| `signature.go` | Подпись запросов и генерация секретов |
| `config.go` | Чтение настроек из переменных окружения |

## Путь одного события

1. Приложение шлёт `POST /events` с типом и данными.
2. В одной транзакции создаётся строка в `events` и по строке в `deliveries` для каждого подходящего подписчика. Транзакция нужна, чтобы не получилось события без доставок, если что-то упадёт посередине.
3. API сразу отвечает `202 Accepted` — «принял, доставлю». Самой отправки в этот момент ещё не было.
4. Один из воркеров находит доставку со статусом `pending`, у которой подошло время, и отправляет её.
5. Если подписчик ответил 2xx — статус `delivered`, готово.
6. Если ответил ошибкой или не ответил за 10 секунд — увеличиваем счётчик попыток и откладываем следующую.
7. Если попытки кончились — статус `dead`. Такие доставки видно в `GET /deliveries?status=dead`, и их можно отправить заново через `POST /deliveries/{id}/retry`, когда подписчик починится.

## Почему несколько воркеров не отправляют одно и то же

Это самое интересное место. Воркеров по умолчанию 4, они работают одновременно (каждый — отдельная горутина) и все смотрят в одну таблицу. Наивно было бы сделать так: воркер выбирает строку, отправляет, помечает отправленной. Но тогда два воркера могут одновременно выбрать одну и ту же строку, и подписчик получит событие дважды.

Решение — в запросе, которым воркер берёт работу:

```sql
SELECT ... FROM deliveries
WHERE status = 'pending' AND next_attempt_at <= now()
ORDER BY next_attempt_at
LIMIT 1
FOR UPDATE OF d SKIP LOCKED
```

- `FOR UPDATE` блокирует найденную строку до конца транзакции;
- `SKIP LOCKED` говорит остальным воркерам: «заблокированные строки просто пропускай, бери следующую».

Получается, что каждый воркер берёт свою строку и никто никого не ждёт. Транзакция держится, пока идёт HTTP-запрос, и закрывается уже вместе с обновлением статуса.

Бонус такого подхода: если воркер умрёт посреди отправки (упал процесс, выключили сервер), транзакция откатится сама, блокировка снимется, и доставку подхватит другой воркер. Отдельно следить за «зависшими» задачами не нужно.

Это проверяет тест `TestTwoWorkersDoNotSendTheSameDelivery`: 20 событий, 4 воркера параллельно — получатель должен получить ровно 20 запросов.

## Повторы и экспоненциальная задержка

Если сразу повторять упавший запрос, мы только добьём подписчику и без того лежащий сервер. Поэтому каждая следующая попытка ждёт в два раза дольше:

| Попытка | Ждём перед следующей |
|---|---|
| 1 | 10 секунд |
| 2 | 20 секунд |
| 3 | 40 секунд |
| 4 | 80 секунд |
| ... | но не больше часа |

Это функция `backoff` в `worker.go`. Время следующей попытки записывается в `next_attempt_at`, и воркер просто не видит доставку, пока это время не наступит.

Что считается ошибкой: любой ответ не 2xx, таймаут (10 секунд) или ошибка соединения.

## Подпись: как подписчик понимает, что запрос от нас

URL подписчика — публичный, кто угодно может прислать туда POST с фейковым «оплата прошла». Чтобы этого не случилось, каждый запрос подписывается.

При создании подписки сервис генерирует случайный секрет и отдаёт его один раз. Дальше к каждому запросу добавляются заголовки:

```
X-Webhook-Id: 42
X-Webhook-Timestamp: 1700000000
X-Webhook-Signature: sha256=3dd1b9ae...
```

Подпись — это HMAC-SHA256 от строки `timestamp + "." + тело запроса` с секретом в качестве ключа. Подписчик знает секрет, считает то же самое у себя и сравнивает. Не совпало — запрос не от нас.

Время входит в подпись, чтобы перехваченный старый запрос нельзя было прислать повторно: подписчик отбрасывает запросы старше нескольких минут. Пример такой проверки — в `examples/receiver/main.go`.

## Как сервис останавливается

При остановке (Ctrl+C или `docker stop`, который шлёт SIGTERM):

1. `signal.NotifyContext` отменяет общий контекст.
2. HTTP-сервер перестаёт принимать новые запросы и дожидается текущих (`server.Shutdown`, максимум 15 секунд).
3. Воркеры видят отменённый контекст и не берут новую работу, но ту доставку, что уже отправляют, доводят до конца — поэтому внутри `processOne` используется свой контекст, а не общий.
4. `sync.WaitGroup` ждёт, пока все воркеры выйдут, и только потом программа завершается.

Так доставка не обрывается на середине и не считается неудачной попыткой только из-за того, что мы перезапускали сервис.

## Тесты

- `signature_test.go` — подпись сверяется с заранее посчитанным через `openssl` значением, плюс проверка задержек между попытками. Базы не требуют.
- `integration_test.go` — работают с настоящим PostgreSQL: доставка с проверкой подписи, повторы после 500, переход в `dead` и ручной повтор, параллельные воркеры, валидация. Вместо настоящего подписчика поднимается `httptest.Server`, которому можно сказать «первые два раза ответь 500».

Интеграционные тесты пропускаются, если не задан `TEST_DATABASE_URL`. `make test-integration` сам поднимает Postgres в Docker и создаёт отдельную базу `webhooks_test`.
